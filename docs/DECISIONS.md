# Architecture Decision Records

One line per decision that the project plan does not already fix: what, why, what was rejected.

| # | Decision | Why | Rejected |
| --- | --- | --- | --- |
| 1 | Region us-east-1 for every stack. | EC2 access is already validated in this account and region; all planned services are available there. | Other regions: no latency or data residency requirement in a simulated city. |
| 2 | AWS Budget of 25 USD per month, credits and refunds excluded, no e-mail notifications. | Credits would hide real spend; spend is checked on demand with Budgets and Cost Explorer instead of alerts. | Budget including credits (would show near zero); e-mail alerts (not wanted). |
| 3 | Bootstrap stack `infra/backend` keeps its own state locally; all other stacks use the S3 bucket with `use_lockfile`. | The bucket cannot store the state of the stack that creates it; S3 native locking removes the need for a DynamoDB lock table. | DynamoDB lock table (deprecated pattern, extra resource). |
| 4 | Backend settings passed through an untracked `infra/backend.hcl` (partial backend configuration), with a committed `.example`. | Keeps the bucket name out of the public repository and lets each stack share one file. | Hardcoded bucket name in every stack. |
| 5 | State bucket hardening: SSE-S3, versioning with 30-day expiry of old versions, public access block, owner-enforced objects, TLS-only bucket policy. | Free controls that protect state files, which contain resource identifiers. | SSE-KMS with a customer key (monthly key cost, no extra benefit here). |
| 6 | Lambda concurrency increase requested from 10 to 1000 during Phase 1. If not granted before the billable session, the consumers are designed to fit in 10 concurrent executions with batching. | The account default of 10 is shared by both MSK consumer groups and all lifecycle and WebSocket handlers. | Waiting for the increase before building. |
| 7 | Python 3.13 for Lambda code, the simulator image and every local test. | Matches a current Lambda runtime; the workstation interpreter is 3.14 and has no venv support. | Testing on 3.14 and deploying on another version. |
| 8 | Common code (event names, bus, MSK decoding, Kafka client factory) lives in `services/shared` and is copied into each Lambda package at build time. | One definition of event names and topics for all functions and the simulator. | A Lambda layer (one more versioned resource for about 150 lines); copy-pasted modules. |
| 9 | H3 resolution 7 cells (about 5 km2) are the pricing zones; nearest-driver search uses Redis GEOSEARCH, not H3. | H3 gives a stable zone id for supply, demand, surge and the Athena demand query; Redis geo commands already answer "nearest within radius" in one call. | H3 k-ring expansion for nearest search (duplicates what GEOSEARCH does); resolution 8 zones (about one driver per zone or less with 20 drivers). |
| 10 | A driver is reserved with Redis `SET claim:<driver> NX EX 30` before assignment. | Atomic: two concurrent rides can never get the same driver; the TTL covers the gap until the simulator reports the driver as en route. | Removing the driver from the GEO set only (a late "available" position would add it back). |
| 11 | Assignments reach the simulator through a Kafka topic (`ride-assignments`) produced by the matching function. | The simulator runs on EKS and already uses Kafka; EventBridge cannot target a pod directly without an extra queue or public HTTP endpoint. | SQS (a service not in the plan); polling DynamoDB from the simulator. |
| 12 | Driver positions reach the UI as a `PositionsSnapshot` EventBridge event emitted by the matching consumer once per batch, delivered by the same notifier as lifecycle events. | One push path for everything the UI shows; the notifier runs outside the VPC and only needs API Gateway and DynamoDB. | A third Kafka consumer that pushes to WebSocket; the matching function calling API Gateway directly from the VPC. |
| 13 | The notifier broadcasts every event to every open connection; the UI filters by client. | The demo has one or two connected screens; per-client routing would add an index for no benefit. | A connections table keyed by client id. |
| 14 | Lifecycle transitions may skip forward but never go back; late events are ignored and logged. | EventBridge does not guarantee ordering; DynamoDB conditional writes enforce the allowed previous states. | Strict one-step transitions (would reject valid rides when two events race). |
| 15 | The simulator compresses time 3x; `RideMatched` carries the real OSRM road ETA, `DriverEnRoute` carries `sim_eta_s`. | A ride completes in about 3 minutes on screen, while prices and ETAs stay based on real road times. | Real time (a demo ride would take 10 minutes or more). |
| 16 | Fares are illustrative: KES 100 base, 40 per km, 4 per minute, KES 200 minimum. Surge adds 0.25 per missing driver (need = 1 available driver plus 1 per request in the last 10 minutes in the zone), capped at 3.0. | Simple enough to verify by hand in the proof outputs. | Opaque multipliers. |
| 17 | Local harness (`local/harness.py`) runs the real handler functions with local stand-ins for EventBridge, the MSK event source mappings, API Gateway WebSocket, DynamoDB and S3. | The full flow is tested offline before any billable resource exists. | LocalStack (heavier, MSK and EKS emulation not needed). |
| 18 | OSRM v6.0.0 image (amd64 and arm64), MLD algorithm, graph built from the Geofabrik Kenya extract clipped to a Nairobi bounding box with osmium. | Clipping keeps preprocessing within the 7.7 GiB available to Docker; the arm64 image allows Graviton nodes. | Whole-Kenya graph (larger memory for no demo benefit). |
| 19 | Synthetic ride history is generated as gzip JSON lines partitioned by `dt`, with OSRM road distances and the project's pricing rules, seed 42, labeled `synthetic` in the table name and every row. | A few thousand rows; JSON keeps the live and synthetic tables on one schema. | Parquet (adds a large dependency for 336 KB of data). |
| 20 | MSK provisioned with 2 x kafka.t3.small (Kafka 3.9.x, ZooKeeper mode) over MSK Serverless. | Official us-east-1 prices: USD 0.0456 per broker-hour (0.0912 for two) against USD 0.75 per cluster-hour plus USD 0.0015 per partition-hour for Serverless. ZooKeeper mode because the CloudFormation reference states kafka.t3.small cannot be selected for KRaft clusters. | MSK Serverless; m7g.large brokers; KRaft. |
| 21 | One NAT gateway (USD 0.045 per hour plus USD 0.005 for its public IPv4) with free S3 and DynamoDB gateway endpoints. | The MSK event source mapping in on-demand mode needs a path from the cluster subnets to Lambda and STS (NAT or PrivateLink). Interface endpoints for Lambda, STS and EventBridge in two AZs cost USD 0.06 per hour and would still leave ECR pulls and the simulator without egress. One NAT covers all of it for less. | Interface endpoints (USD 0.06/h and incomplete); ESM provisioned mode (USD 0.185 per event poller unit hour); one NAT per AZ (no availability requirement for a demo). |
| 22 | EKS with one t4g.medium Graviton node (2 of the 32 vCPU quota) and arm64 images. | OSRM measured at 108 MiB after load and the simulator is small; one node holds both. USD 0.0336 per hour against USD 0.0416 for t3.medium. | Fargate (not costed in detail: pod compute for two small pods may be similar, but a managed node keeps OSRM reachable on a NodePort without a load balancer); two nodes. |
| 23 | OSRM is reached by the matching functions through a NodePort on the node's private IP, read by the app stack at apply time. | No load balancer charge and no load balancer controller to install. The node group is fixed at one node for the session; if the node is replaced, the app stack is re-applied. | Internal Network Load Balancer (hourly plus capacity units, plus a controller and its IAM role). |
| 24 | ElastiCache Redis OSS 7.1 on one cache.t4g.micro, TLS in transit and encryption at rest, no replica. | USD 0.016 per hour; the index is rebuilt from the position stream within a second if lost. | Replica with failover (doubles the cost for no demo benefit). |
| 25 | `driver-positions` has one partition. | With Lambda concurrency at 10 for the account, each consumer group then uses at most one concurrent invocation, leaving room for the other functions. 20 positions per second fit easily in one partition. | More partitions (would multiply concurrent consumers against a limit of 10). |
| 26 | Event source mappings: batch size 500; batching window 1 s for matching, 10 s for archival. | Matching needs fresh positions; archival writes fewer, larger S3 objects. | Same window for both. |
| 27 | Only the two matching functions run inside the VPC. The archiver, lifecycle, notifier and WebSocket functions run outside it. | Only matching needs Redis, OSRM and the MSK producer. MSK event source mappings do not require the function itself to be in the VPC. | All functions in the VPC (more ENIs, NAT traffic for nothing). |
| 28 | IAM wildcards kept: EC2 network interface actions on "*" for VPC functions and event source mappings; in the cluster stack, the MSK cluster UUID segment of the cluster, topic and group ARNs. | The EC2 create and describe actions do not support resource-level permissions. The MSK UUID is unknown until the data stack is applied, and the cluster and data stacks are applied in parallel; every other segment (account, region, cluster name) is fixed. | Admin or service-wide wildcards. |
| 29 | WebSocket API: stage throttling (burst 20, rate 10 requests per second) and a 40-character random token checked on $connect, generated by Terraform at deploy time, stored only in state, the function environment and the untracked UI `.env.local`. | The API is public while the stack is up; this keeps casual use and floods out without adding Cognito for a one-session demo. | A Lambda authorizer (one more function for the same check); no protection. |
| 30 | EKS API endpoint public but restricted to the operator's /32, private endpoint enabled; access entries (API mode) instead of the aws-auth ConfigMap. | kubectl from the workstation without opening the control plane to the internet. | Fully public endpoint; private only (would need a bastion or VPN). |
| 31 | No customer-managed KMS keys: MSK, DynamoDB, S3, ElastiCache and EBS use AWS managed or owned keys; EKS secrets are not envelope-encrypted with a customer key. | Encryption at rest is still on everywhere; a customer key costs USD 1 per month each and adds key policy work with no benefit for synthetic data. | Customer-managed keys. |
| 32 | CloudWatch log groups created by Terraform with 1-day retention; no MSK broker logs. | Logs are only needed during the session; created up front so they are tagged and destroyed with the stack. | Default never-expire log groups created by Lambda. |
| 33 | ECR repositories with immutable tags (git commit) and basic scan on push. | The deployed image is traceable to a commit; basic scanning is free. | Mutable `latest` tags. |
